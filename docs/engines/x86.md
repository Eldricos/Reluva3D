# The x86 interpreter

Elite Force's single player ships its game logic as 32-bit Windows DLLs
(`efgamex86.dll`, `efuix86.dll`). Rather than reimplement that logic,
Reluva runs the original code in an interpreter of the x86 processor, as
it runs Holomatch's QVM bytecode: the code stays in the user's copy, on
any machine Reluva builds for. It's new code, written from Intel's
published instruction set reference and Microsoft's published PE/COFF
specification and API documentation.

## What's there (`src/common/x86`)

- **`cpu.h`, `cpu.cpp`: the processor.** The 32-bit integer instructions
  (with 16-bit operands), string instructions with `rep`, the bit
  instructions, `CPUID` (it reports a Pentium) and the FS segment
  (Windows' thread information block). Its memory is one flat arena from
  address 0 whose first page faults, so null pointers are caught. Faults
  (bad memory, division by zero, an instruction not implemented) end the
  call with an error naming the address.
- **`fpu.cpp`: the x87 floating point unit.** Its registers are doubles:
  Windows runs the x87 at 53-bit precision, at which its results are a
  double's. The 80-bit format is converted where it's loaded or stored.
  24-bit precision is followed if a program sets it.
- **Native functions.** The engine's functions, and stand-ins for the
  system's, live at reserved addresses at the top of memory; a call there
  runs a C++ function, which reads its arguments off the stack and sets
  the result. They may call back into emulated code.
- **`win32.h`, `win32.cpp`: a Windows process.** It loads a DLL or an EXE
  (relocated if its preferred address is taken), binds its imports
  (functions, and variables for data imports), and runs its `DllMain`, or
  an EXE's entry point. The stack and thread blocks sit at the top of
  memory, so an EXE without relocations can have 0x400000. The KERNEL32
  functions a Visual C++ 6 C runtime calls are stood in for:
  - the heap and pages;
  - the version: Windows XP, so the runtime uses the system's heap;
  - the command line, environment and start-up details;
  - text conversion for code page 1252;
  - the standard handles, whose output is passed on.

  An import nothing stands in for is bound to a function that fails the
  run, naming it. Threads and windows aren't there yet.
- **`win32_files.cpp`: files.** The program's Windows paths become paths on
  this machine through `mapPath`, which the engine provides. These are
  stood in for:
  - handles: `CreateFileA`, `ReadFile`, `WriteFile`, `SetFilePointer`,
    `GetFileSize`, `GetFileTime`, and the 16-bit era's `OpenFile`/`_lread`;
  - searches (`FindFirstFileA` with wildcards);
  - memory-mapped views: copies, as these programs only read them;
  - the current folder;
  - the drives: C: and a CD-ROM drive, whose volume label the engine sets
    so a game's CD check passes.
- **`msvcrt.h`, `msvcrt.cpp`: MSVCRT.dll**, for programs that link
  Visual C++'s C runtime dynamically, written from Microsoft's
  documentation of each function:
  - memory, strings and characters (the "C" locale);
  - numbers, and Visual C++'s `rand` (so random choices come out as they
    did);
  - maths, including the `_CI` functions that take their operands on the
    x87 stack, `_ftol` and `_controlfp`;
  - `printf` and `scanf` formatting, and `FILE` files over the process's
    file handles;
  - `_stat` with Visual C++ 6's structure, and time;
  - the start-up helpers (`__getmainargs`, `_initterm`, its variables);
  - `_EH_prolog`'s exception frame, and the `exception` class.

  Throwing a C++ exception, or reaching an exception handler, ends the run
  naming the type thrown, since dispatching isn't done yet.
- **`win32_system.cpp`: the system.** System information (one Pentium
  II-class processor, 256 MB), the performance counter (microseconds),
  `MulDiv`, the computer's name, and `GetDateFormatA`/`GetTimeFormatA` with
  English (United States) pictures. There's one thread, so critical
  sections do nothing, `Sleep` returns at once and a wait on an event finds
  it signalled.
- **`win32_user.cpp`: USER32 and GDI32.** Window classes and windows, kept
  as records (procedure, place, size, visibility) that the engine can show
  as it likes. Making one sends `WM_NCCREATE` and `WM_CREATE`. Showing it
  first activates it (`WM_ACTIVATEAPP`, `WM_ACTIVATE`, `WM_SETFOCUS`).
  Other pieces:
  - one message queue, which the engine posts its input to and
    `PeekMessageA` reads, calling `idle` when it's empty;
  - `DispatchMessageA` and `TranslateMessage`;
  - `DefWindowProcA` destroys a window it's asked to close;
  - frames and captions are Windows 98's sizes;
  - the mouse pointer, and the desktop's size and colour depth, which the
    engine sets;
  - `MessageBoxA` is reported and answered so the program goes on.
- **`win32_registry.cpp`: the registry and COM.** An in-memory registry,
  seeded with the installed locales. The engine can add an installer's
  values and hear of the program's writes. `CoCreateInstance` asks the
  engine's `createComObject`; with none, no class is registered.
- **`com.h`, `com.cpp`: COM objects.** An interface is a table of method
  names and argument counts. `ComHost` builds its vtable of native
  functions in the program's memory, and makes the interface pointers,
  each dispatching to a C++ `ComObject`.
  - QueryInterface, AddRef and Release are done here: an object is freed
    when its count reaches 0.
  - A method an object doesn't stand in for ends the run, naming it.
- **Input** (`win32_user.cpp`): the engine passes the mouse and keyboard
  to the process with `mouseMoveTo`, `mouseButton`, `mouseWheel` and
  `key`.
  - They become window messages to the main window (`WM_MOUSEMOVE`,
    button presses, double clicks for classes with `CS_DBLCLKS`,
    `WM_KEYDOWN`/`WM_KEYUP` with the scan code in lParam).
  - They also update the pointer (within `ClipCursor`'s rectangle) and
    what `GetKeyState` and `GetAsyncKeyState` report.
  - `rawInput` listeners (DirectInput) hear the same movements, buttons
    and keys.
- **`directx/dinput.cpp`: DINPUT.dll**, DirectInput up to DirectX 7.
  - The system mouse (3 axes, 4 buttons) and keyboard (256 keys by scan
    code), read through the program's data format (the `c_dfDIMouse` and
    `c_dfDIKeyboard` kinds, or its own).
  - Read either as an immediate state (relative or absolute axes) or as a
    buffer of changes (`DIPROP_BUFFERSIZE`, `GetDeviceData`).
- **`directx/`: DDRAW.dll**, DirectDraw and Direct3D 7 (in software): see
  docs/engines/alphateam.md.
- **`a3d.cpp`: Aureal A3D** (the `A3dApi` COM class, A3D 3 and its
  version-4 interface). Names, method orders and constants come from
  Aureal's public SDK documentation (`ia3dapi.h`). Each method a program
  calls was checked against its call site: the vtable slot and the number
  of words pushed.
  - Sources hold their wave data (PCM, 8 or 16 bits, mono or stereo) in
    the program's memory. The program fills it through `Lock` and
    `Unlock`.
  - A playing source's position follows the process's clock (`milliseconds`)
    at its rate and pitch. It wraps round when looped, and a source played
    once stops at its end. `GetWavePosition`, `GetWaveTime` and `GetStatus`
    report it, so programs that stream into a source or wait for it to
    finish see it move.
  - What a source has played is handed to the mixer as a `SoundStream`
    (`audio::Mixer::playStream`). That happens on every call into A3D, the
    same calls a program makes to keep its streaming buffers filled.
  - A positioned source gets a gain from its distance to the listener
    (inverse distance beyond its minimum) and a pan from its side.
  - Geometry (occlusion, reflections), materials, cones, Doppler and EQ
    are accepted and not heard. `IsFeatureAvailable` reports none.
  - Wave events (`SetWaveEvent`) are set as play passes their offsets. They
    are the only events whose state the process keeps
    (`Win32Process::trackEvent`). Every other event reads as set to a
    wait, since threads take turns and none could set it while another
    waits. Programs stream by them: NiA3dSound's streaming manager puts
    one at the middle of a source's buffer and refills half the buffer
    each time it's set. Read as always set, it raced through the whole
    file in a few seconds and the line was cut short.
- Threads (`_beginthread`) take turns with the main thread, so no two
  ever run at once (`Win32Process::startThread`, `runThreads`):
  - Each has its own registers, stack and thread information block (a
    `Cpu::Context`).
  - When the main thread calls `Sleep`, `PeekMessage` or `GetMessage`,
    each thread that's due runs (`Cpu::resume`).
  - A thread runs until its own `Sleep`, which yields (`Cpu::yield`)
    until its wake time, or until it ends (`_endthread`, or returning from
    its function).
  - Code a thread shares with the main thread is never run by both at
    once, so the critical sections can stay no-ops. `testThreads` checks
    the turns.
- `LoadLibraryA` loads a DLL from the program's files (through
  `mapPath`) and runs its start-up. `GetProcAddress` reports the names it
  can't find to `output`.
- **`msvcp60.h`, `runtime/`: MSVCP60.dll**, Visual C++ 6's C++ library.
  Programs build its classes inline and derive from them, so it isn't
  stood in for natively. `runtime/msvcp60.cpp` is our own replacement,
  written from the C++ standard with the layouts measured from the
  programs (docs/engines/alphateam.md lists them). `runtime/build_msvcp60.sh`
  builds it with clang into a real DLL (`runtime/msvcp60_dll.h`, embedded),
  importing only MSVCRT; `loadMsvcp60` loads it into a process.

## Testing

- `tests/test_common.cpp` runs hand-encoded instructions.
- It also runs a DLL built from `tests/x86/testdll.c` by
  `tests/x86/build_testdll.sh`: clang for the Pentium, x87 only, linked
  by lld-link. Its 20 tests, each run on 12 inputs, must give what the
  same C gives built natively (integer and 64-bit arithmetic, division,
  shifts, sorting, CRC, recursion, function pointers, float arithmetic and
  conversions).
  - The script writes the DLL and the native results to
    `tests/data/x86_testdll.h`.
  - The DLL is also loaded a second time, so that it is relocated.
- It calls MSVCRT's and the file stand-ins as a program would:
  - strings;
  - `rand`'s sequence;
  - `sscanf` and `sprintf`;
  - `_ftol` and `_CIpow` on the x87 stack;
  - `_EH_prolog`'s frame;
  - `fopen` relative to the program's folder;
  - a mapped view, a search, and the CD's label.
  - `MulDiv`'s rounding, date and time text, the performance counter.
- It makes a window with a native window procedure and checks the
  messages it gets, the queue, frame sizes, and closing. It also checks
  the registry's keys, values, sizes and enumeration, and
  `CoCreateInstance`.
- `testDirectX` makes a fullscreen DirectDraw and Direct3D 7 device and
  draws, checking the pixels of the frame shown.
- `testA3d` creates A3D through `CoCreateInstance` and makes a source. It
  fills the source through a `Lock` that wraps round, plays it once and
  then looped as the clock moves, and checks its position, its status,
  the samples the mixer hears, and a wave event set as play passes it.
- `testInput` checks the messages input becomes, double clicks, key
  states and `ClipCursor`. It also checks DirectInput's mouse (its state,
  its movement since the last read, its buffer) and keyboard.
- It loads our MSVCP60 and calls it as a program would: strings in Visual
  C++ 6's layout, an `ifstream` reading lines and bytes, a string stream
  buffer growing as it's written (with a vftable built as the programs
  build theirs), and `cerr` with numbers and `endl`.
- `reluva-tool x86-run <dll> [-call Export args...]` loads a DLL and runs
  its start-up and, if asked, an export. An argument `table` passes a
  table of functions that print each call made to them. It's for seeing
  how far a game's DLL gets and what it asks of the engine. A failure
  prints the addresses of the last instructions run.

## Known limits

- Structured exception handling isn't dispatched: `RaiseException` and
  `RtlUnwind` end the run.
- No MMX or SSE (the game DLLs predate their common use).
- The interpreter checks each memory access. Instructions are decoded
  once and kept, see "The decoded-instruction cache" below.

## The decoded-instruction cache

`src/common/x86/cpu_cache.cpp`. Instructions run in blocks: from an
address, the instructions up to the first that may go elsewhere (a jump,
call or return, or one run from its bytes that might), at most 16 of
them. Blocks are kept in a direct-mapped table of 32768, by their first
instruction's address. Each instruction in a block has its operands
decoded once (a register, or memory as base, index, scale and
displacement; the immediate) and a handler of its own. Each handler is
specialised by operand size, ALU operation or condition, so flags are
worked out without the general `alu()` switch. Handlers exist for:

- the moves (88–8B, C6/C7, B0–BF, A0–A3), LEA, MOVZX/MOVSX;
- the ALU operations in all their forms (00–3D, 80/81/83), TEST (84/85,
  A8/A9, F6/F7 /0), INC/DEC, IMUL (0F AF, 69, 6B);
- PUSH/POP, LEAVE;
- Jcc, JMP, CALL and RET (and indirect through FF);
- the shifts and rotates, SETcc, CDQ, NOP;
- the commonest x87 ones: FLD/FST/FSTP of floats and doubles, FILD of
  32 bits, the arithmetic on memory and registers, FXCH, FCHS, FABS,
  FLD1, FLDZ, FNSTSW AX.

They also cover the FS and operand-size (66) prefixes. Everything else
runs from its bytes as before (`Cpu::execute`). Those that can't go
elsewhere and whose length is plain (the other x87 instructions, NOT,
NEG, MUL, DIV and IDIV, RDTSC, REP string operations) do so without
ending their block.

A block keeps its instructions' bytes and is made again when they're not
what they were. That's checked each time it runs, a few 64-bit compares.
So code that changes is always run as it now is, however it was written:
by the program, or by a native such as a loader's `memcpy`. Instructions
are still counted one by one, so a run on an instruction clock repeats
exactly whatever the blocks.

Natives, and runs with a `trace` callback, go one instruction at a time
as before (`Cpu::step`). `Cpu::cacheOn = false` runs everything from the
bytes. The tests run the instruction tests and the test DLL both ways.
They also run 3000 random sequences of 40 instructions, with operands in
registers and memory, both ways, and compare registers, flags, the x87
unit and memory afterwards.

## First results with the retail DLLs (1.2)

- Both DLLs' start-up runs to completion: `efuix86.dll` in about 9,800
  instructions, `efgamex86.dll` in about 172,000. Every KERNEL32 function
  they call has a stand-in.
- `GetUIAPI` returns a table of 12 functions, without calling the engine.
- `GetGameAPI` returns a structure shaped like Jedi Outcast's
  `game_export_t` (codeJK2/game/g_public.h, GPL):
  - an API version, 6;
  - 13 functions: JK2 has 14, one of which (`ConnectNavs`) Elite Force
    probably doesn't;
  - then, probably, `gentities` (0 until the game is started),
    `gentitySize` (0x420, 1056 bytes) and `num_entities`.

  It makes two calls to the engine's table, to slots 14 and 15. Jedi
  Outcast's `GetGameAPI` ends by reading a file through its import table
  (`FS_ReadFile`, then `FS_FreeFile`, at slots 15 and 16 there). This is
  to be confirmed from the arguments.

The full interface between the DLLs and the engine, as later read from the
retail executable, is in
[../formats/idtech3/eliteforce-sp-interface.md](../formats/idtech3/eliteforce-sp-interface.md).

## Running the single-player game

`src/engines/idtech3/eliteforce/sp_game_host.{h,cpp}` runs `efgamex86.dll`'s
server game:

- **Loading.** It loads the DLL, calls `GetGameAPI` with native functions
  in the engine's 40 slots, and checks the API version.
- **Starting a level.** It calls `Init` with the map's entity text, lets
  the player join (`ClientConnect`, then `ClientBegin`), and runs frames.
- **Reused from Holomatch.** Collision, entity linking, area portals and
  traces come from the Holomatch host, with the single-player entity layout.
- **Cvars.** The engine's cvar structures live in emulated memory and are
  kept up to date, since the game reads them directly.
- **printf-style calls.** `Printf`, `Error` and `SendServerCommand` are
  formatted from the emulated stack (`src/common/x86/format.cpp`).

`reluva-tool sp-run <game folder> <map>` runs it and reports what the game
did. It finds the DLL beside the game folder unless given `-dll`.

Status: on borg1 the retail game starts the level and runs.

- `Init` parses its data files, starts ICARUS and spawns 561 entities,
  371 of them linked into the world. That's about 83 million
  instructions.
- The player joins.
- Frames run, about 250,000 instructions each.
- The game sets 103 configstrings: the music, models and so on.

The server game also calls into its client half (`cg_viewsize`, sounds),
through the system call function `dllEntry` hands it, so that's set up at
load.

Speed: about 50 million instructions a second in a Release build before
the decoded-instruction cache, about 1.5 times that with it. A Debug build
is much slower.

## Playing single player

The **Single player** page (`src/engines/idtech3/sp_play_viewer.cpp`)
appears when `efgamex86.dll` is in the install folder. It lists the maps
that aren't Holomatch's and starts at borg1.

- **What it runs.** Each level runs the retail server and client game as
  `sp-run -cgame` does.
- **Frames.** The client game's scenes and pictures are drawn by the same
  scene drawer as the Play page's. The client game's view and scene
  entities are laid out as in Holomatch: the 112-byte `refdef_t` and the
  152-byte `refEntity_t`, as the engine copies them.
- **Input.** Keys and mouse go through the player's bindings, as on the
  Play page:
  - movement and buttons become the 28-byte user command;
  - other commands go to the client game first, then the server game.
- **Keys.** Ctrl+R restarts the level, Ctrl+PgUp/PgDn change map, Ctrl+I
  hides the info line, and Esc returns to the menus.

Not yet:

- sound;
- the saved-game picture and rotated pictures;
- wall marks (`CM_MarkFragments`);
- the ambient sound sets;
- `R_LightForPoint` (a plain light for now);
- saving and loading games;
- the menus' single-player screens (`efuix86.dll`).
