# The x86 interpreter

Elite Force's single player ships its game logic as 32-bit Windows DLLs
(`efgamex86.dll`, `efuix86.dll`). Rather than reimplement that logic,
Reluva runs the original code in an interpreter of the x86 processor, as
it runs Holomatch's QVM bytecode: the code stays in the user's copy, on
any machine Reluva builds for. It's new code, written from Intel's
published instruction set reference and Microsoft's published PE/COFF
specification and API documentation.

## What's there (`src/common/x86`)

- **`cpu.h`, `cpu.cpp`: the processor.** The 32-bit integer instructions
  (with 16-bit operands), string instructions with `rep`, the bit
  instructions, `CPUID` (it reports a Pentium) and the FS segment
  (Windows' thread information block). The segment registers hold their
  selectors and are pushed, popped and moved, but the model is flat. Its memory is one flat arena from
  address 0 whose first page faults, so null pointers are caught. Faults
  (bad memory, division by zero, an instruction not implemented) end the
  call with an error naming the address.
- **`fpu.cpp`: the x87 floating point unit.** Its registers are doubles:
  Windows runs the x87 at 53-bit precision, at which its results are a
  double's. The 80-bit format is converted where it's loaded or stored.
  24-bit precision is followed if a program sets it.
  - A 64-bit integer loaded with FILD is kept exactly beside its double,
    and FISTP stores it back unchanged. Programs of the time copy memory
    8 bytes at a time that way (Need for Speed III's `memcpy` does), and
    a double can't hold every 64-bit integer.
  - FSAVE and FRSTOR keep such integers exact too.
- **Native functions.** The engine's functions, and stand-ins for the
  system's, live at reserved addresses at the top of memory; a call there
  runs a C++ function, which reads its arguments off the stack and sets
  the result. They may call back into emulated code.
- **`win32.h`, `win32.cpp`: a Windows process.** It loads a DLL (relocated
  if its preferred address is taken), binds its imports, and runs its
  `DllMain`. The KERNEL32 functions a Visual C++ 6 C runtime calls are
  stood in for:
  - the heap and pages;
  - the version: Windows XP, so the runtime uses the system's heap;
  - the command line, environment and start-up details;
  - text conversion for code page 1252;
  - the standard handles, whose output is passed on.

  An import nothing stands in for is bound to a function that fails the
  run, naming it. The game DLLs get files and windows from the engine
  instead.
- **Executables** (`Win32Process::run`). A program's entry point runs on
  the main thread until it ends the process:
  - it's loaded at 0x400000, which is kept clear;
  - its path and command line are set by the engine (`setProgram`);
  - zero-filled sections are left as zeros whatever raw size the file
    gives them (Watcom's linker gives one);
  - resources can be read (`findResource` in `common/pe.cpp`: the
    version information, for one).
- **Files** (`win32_files.cpp`). Each drive letter the program sees is a
  host folder:
  - names are matched ignoring case;
  - what the program writes can be kept in a folder of its own, so the
    game's folder stays as it was;
  - a CD drive is read-only;
  - the stand-ins cover files, searches, folders, drives, volume labels
    and read-only file mappings.
- **Threads** (`win32_threads.cpp`). The program's threads take turns on
  the one processor. Each runs on a host thread of its own, with its own
  stack and information block; only the one holding the turn runs, and
  the processor's registers (`Cpu::Context`) change with it. As on
  Windows:
  - the runnable thread of highest priority runs, in turn with those of
    the same priority;
  - one that wakes a thread of higher priority hands over at once;
  - otherwise they change over when one waits, and every few thousand
    instructions (`slice`), so that a thread polling a variable lets the
    others run.

  The stand-ins cover events, mutexes, critical sections, the waits,
  thread-local storage, and the multimedia timer (`timeSetEvent`), whose
  callbacks run on one timer thread of time-critical priority, as WINMM's
  do.

## Testing

- `tests/test_common.cpp` runs hand-encoded instructions.
- It also runs a DLL built from `tests/x86/testdll.c` by
  `tests/x86/build_testdll.sh`: clang for the Pentium, x87 only, linked
  by lld-link. Its 20 tests, each run on 12 inputs, must give what the
  same C gives built natively (integer and 64-bit arithmetic, division,
  shifts, sorting, CRC, recursion, function pointers, float arithmetic and
  conversions).
  - The script writes the DLL and the native results to
    `tests/data/x86_testdll.h`.
  - The DLL is also loaded a second time, so that it is relocated.
- `tests/test_common.cpp` also checks the FPU's exact 64-bit copies, the
  segment registers, and the drives' paths.
- `reluva-tool nfs-host` runs a whole program, Need for Speed III, with
  its threads ([nfs.md](nfs.md), Phase 4).
- `reluva-tool x86-run <dll> [-call Export args...]` loads a DLL and runs
  its start-up and, if asked, an export. An argument `table` passes a
  table of functions that print each call made to them. It's for seeing
  how far a game's DLL gets and what it asks of the engine. A failure
  prints the addresses of the last instructions run.

## Known limits

- Structured exception handling isn't dispatched: `RaiseException` and
  `RtlUnwind` end the run. A program that reads low memory to tell
  Windows 95 from NT can be let do so (`readableFirstPage`), as Windows
  95 and 98 allow.
- No MMX or SSE (the game DLLs predate their common use).
- The interpreter decodes each instruction as it runs it. It doesn't
  translate code ahead. Where the time goes and what was done about it is
  under **Speed** below.

## First results with the retail DLLs (1.2)

- Both DLLs' start-up runs to completion: `efuix86.dll` in about 9,800
  instructions, `efgamex86.dll` in about 172,000. Every KERNEL32 function
  they call has a stand-in.
- `GetUIAPI` returns a table of 12 functions, without calling the engine.
- `GetGameAPI` returns a structure shaped like Jedi Outcast's
  `game_export_t` (codeJK2/game/g_public.h, GPL):
  - an API version, 6;
  - 13 functions: JK2 has 14, one of which (`ConnectNavs`) Elite Force
    probably doesn't;
  - then, probably, `gentities` (0 until the game is started),
    `gentitySize` (0x420, 1056 bytes) and `num_entities`.

  It makes two calls to the engine's table, to slots 14 and 15. Jedi
  Outcast's `GetGameAPI` ends by reading a file through its import table
  (`FS_ReadFile`, then `FS_FreeFile`, at slots 15 and 16 there). This is
  to be confirmed from the arguments.

The full interface between the DLLs and the engine, as later read from the
retail executable, is in
[../formats/idtech3/eliteforce-sp-interface.md](../formats/idtech3/eliteforce-sp-interface.md).

## Running the single-player game

`src/engines/idtech3/eliteforce/sp_game_host.{h,cpp}` runs `efgamex86.dll`'s
server game:

- **Loading.** It loads the DLL, calls `GetGameAPI` with native functions
  in the engine's 40 slots, and checks the API version.
- **Starting a level.** It calls `Init` with the map's entity text, lets
  the player join (`ClientConnect`, then `ClientBegin`), and runs frames.
- **Reused from Holomatch.** Collision, entity linking, area portals and
  traces come from the Holomatch host, with the single-player entity layout.
- **Cvars.** The engine's cvar structures live in emulated memory and are
  kept up to date, since the game reads them directly.
- **printf-style calls.** `Printf`, `Error` and `SendServerCommand` are
  formatted from the emulated stack (`src/common/x86/format.cpp`).

`reluva-tool sp-run <game folder> <map>` runs it and reports what the game
did. It finds the DLL beside the game folder unless given `-dll`.

Status: on borg1 the retail game starts the level and runs.

- `Init` parses its data files, starts ICARUS and spawns 561 entities,
  371 of them linked into the world. That's about 83 million
  instructions.
- The player joins.
- Frames run, about 250,000 instructions each.
- The game sets 103 configstrings: the music, models and so on.

The server game also calls into its client half (`cg_viewsize`, sounds),
through the system call function `dllEntry` hands it, so that's set up at
load.

## Speed

About 70 million instructions a second in a Release build, measured on
Need for Speed III's start-up and in a race. A Debug build is much
slower.

October 2026, profiled with callgrind and by sampling stacks with gdb.
The first measurement was 33 million a second; each change below was
checked against that (CPU seconds for the same 400 million instructions,
12.0 at the start, 5.5 after):

- **Memory accesses and fetches inline** (`cpu.h`). The bounds check is
  one comparison against the arena's size less its first page. The rare
  cases are out of line: low memory read as 0, or a fault, which builds
  a message. Before this, each access was a call whose fault path forced
  a heavy stack frame. Most of the gain came from this.
- **One test per instruction** for what's due every so often: the next
  thread slice and the instruction limit share one counter.
- **`step()` inlined into `runUntil()`**, its one caller. The large
  function's frame is then set up once a run, not once an instruction.
- **Decoded ModRM operands cached** (`decodeModrm`). Entries are keyed by
  the ModRM byte's address and hold what its bytes say: registers, scale
  and displacement. Each entry also keeps the bytes it was decoded from,
  and is used only while they're unchanged. So code written over, by the
  program or by native code, is never run stale, and nothing has to
  watch for writes.

October 2026, a second round, checked with `nfs-host -deterministic`
(docs/engines/nfs.md): the same end state after 5 billion instructions
from the menus into a race, and the best of several runs' CPU seconds.

- **A change of thread wakes one host thread.** Each emulated thread's
  host thread waited on one condition variable, and every change of
  thread woke all of them (about seven) to find whose turn it was. Their
  wake-ups and the lock they fought over took about 7% of the time. Now
  each thread has its own, and only the next is woken: 18% less CPU time.
- **`step()` inlined with Visual Studio too** (`__forceinline`), which
  ignores the GNU attribute.
- **One `switch` for the opcode.** The runs of opcodes (the ALU group,
  INC and DEC, PUSH and POP, Jcc, MOV with an immediate, x87) were tested
  one by one before the `switch`; they're case labels in it now, so every
  opcode goes through one jump. Prefixes are found with a table rather
  than a chain of tests: 7% less CPU time.
- **Tried, no difference:** ModRM cache entries of 32 bytes with their
  mask (each in one cache line), parity from a table, `decodeModrm`
  inlined.
- **Tried, not kept: whole instructions decoded in blocks.** Each
  instruction's prefixes, opcode, ModRM operand and immediates recorded
  on its first run, in blocks of instructions that follow one another,
  and replayed after that; a block's bytes compared with memory on
  entering it, or not, when nothing could have written code since. It
  gave the same end state, at the same speed: the decoding saved was
  spent waiting for the blocks' records, which miss the processor's
  caches (the race's code made about 330,000 records, against 1 MB of
  L2 per core). A smaller record (20 bytes rather than 48) was slower
  still, from unpacking it. Reading the code's own bytes, as now, keeps
  far less in the caches.

On Windows, one report from a Core i7-6700K with Visual Studio's x64-Release
(RelWithDebInfo, `/Ob1`): 37 million instructions a second in a race, half of
this machine's. Hometown with every opponent and every detail at its highest
took 1.4 to 3.1 million instructions a frame, against about 1.2 million with
the defaults. `CMakeLists.txt` now asks Visual Studio for full inlining
(`/Ob3`) outside Debug, and `CMakePresets.json` gives a true Release and a
clang-cl one; not yet measured there. Clang (Release) ran the deterministic
race about 5% faster than GCC here.

Ideas not taken yet: lazy flags (`eflags` is read and written in about 70
places, so a large change for the few percent its computing takes).

## Playing single player

The **Single player** page (`src/engines/idtech3/sp_play_viewer.cpp`)
appears when `efgamex86.dll` is in the install folder. It lists the maps
that aren't Holomatch's and starts at borg1.

- **What it runs.** Each level runs the retail server and client game as
  `sp-run -cgame` does.
- **Frames.** The client game's scenes and pictures are drawn by the same
  scene drawer as the Play page's. The client game's view and scene
  entities are laid out as in Holomatch: the 112-byte `refdef_t` and the
  152-byte `refEntity_t`, as the engine copies them.
- **Input.** Keys and mouse go through the player's bindings, as on the
  Play page:
  - movement and buttons become the 28-byte user command;
  - other commands go to the client game first, then the server game.
- **Keys.** Ctrl+R restarts the level, Ctrl+PgUp/PgDn change map, Ctrl+I
  hides the info line, and Esc returns to the menus.

Not yet:

- sound;
- the saved-game picture and rotated pictures;
- wall marks (`CM_MarkFragments`);
- the ambient sound sets;
- `R_LightForPoint` (a plain light for now);
- saving and loading games;
- the menus' single-player screens (`efuix86.dll`).
