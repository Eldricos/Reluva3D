# The x86 interpreter

Elite Force's single player ships its game logic as 32-bit Windows DLLs
(`efgamex86.dll`, `efuix86.dll`). Rather than reimplement that logic,
Reluva runs the original code in an interpreter of the x86 processor, as
it runs Holomatch's QVM bytecode: the code stays in the user's copy, on
any machine Reluva builds for. It's new code, written from Intel's
published instruction set reference and Microsoft's published PE/COFF
specification and API documentation.

## What's there (`src/common/x86`)

- **`cpu.h`, `cpu.cpp`: the processor.** The 32-bit integer instructions
  (with 16-bit operands), string instructions with `rep`, the bit
  instructions, `CPUID` (it reports a Pentium) and the FS segment
  (Windows' thread information block). Its memory is one flat arena from
  address 0 whose first page faults, so null pointers are caught. Faults
  (bad memory, division by zero, an instruction not implemented) end the
  call with an error naming the address.
- **`fpu.cpp`: the x87 floating point unit.** Its registers are doubles:
  Windows runs the x87 at 53-bit precision, at which its results are a
  double's. The 80-bit format is converted where it's loaded or stored.
  24-bit precision is followed if a program sets it.
- **Native functions.** The engine's functions, and stand-ins for the
  system's, live at reserved addresses at the top of memory; a call there
  runs a C++ function, which reads its arguments off the stack and sets
  the result. They may call back into emulated code.
- **`win32.h`, `win32.cpp`: a Windows process.** It loads a DLL (relocated
  if its preferred address is taken), binds its imports, and runs its
  `DllMain`. The KERNEL32 functions a Visual C++ 6 C runtime calls are
  stood in for:
  - the heap and pages;
  - the version: Windows XP, so the runtime uses the system's heap;
  - the command line, environment and start-up details;
  - text conversion for code page 1252;
  - the standard handles, whose output is passed on.

  An import nothing stands in for is bound to a function that fails the
  run, naming it. Files, threads and windows aren't there: the game DLLs
  get those from the engine.

## Testing

- `tests/common/unit.cpp (`common.unit.x86`)` runs hand-encoded instructions.
- It also runs a DLL built from `tests/common/x86/testdll.c` by
  `tests/common/x86/build_testdll.sh`: clang for the Pentium, x87 only, linked
  by lld-link. Its 20 tests, each run on 12 inputs, must give what the
  same C gives built natively (integer and 64-bit arithmetic, division,
  shifts, sorting, CRC, recursion, function pointers, float arithmetic and
  conversions).
  - The script writes the DLL and the native results to
    `tests/common/data/x86_testdll.h`.
  - The DLL is also loaded a second time, so that it is relocated.
- `reluva-tool x86-run <dll> [-call Export args...]` loads a DLL and runs
  its start-up and, if asked, an export. An argument `table` passes a
  table of functions that print each call made to them. It's for seeing
  how far a game's DLL gets and what it asks of the engine. A failure
  prints the addresses of the last instructions run.

## Known limits

- Structured exception handling isn't dispatched: `RaiseException` and
  `RtlUnwind` end the run.
- No MMX or SSE (the game DLLs predate their common use).
- The interpreter checks each memory access and decodes each
  instruction as it runs it. That's simple, and fast enough for game
  logic of 2000 on today's machines. Caching decoded instructions could
  speed it up later.

## First results with the retail DLLs (1.2)

- Both DLLs' start-up runs to completion: `efuix86.dll` in about 9,800
  instructions, `efgamex86.dll` in about 172,000. Every KERNEL32 function
  they call has a stand-in.
- `GetUIAPI` returns a table of 12 functions, without calling the engine.
- `GetGameAPI` returns a structure shaped like Jedi Outcast's
  `game_export_t` (codeJK2/game/g_public.h, GPL):
  - an API version, 6;
  - 13 functions (Jedi Outcast's 14 without `ConnectNavs`);
  - then `gentities` (0 until the game is started), `gentitySize` (0x420,
    1056 bytes) and `num_entities`.

  It makes two calls to the engine's table, to slots 14 and 15: it reads
  `ext_data/weapons.dat` (`FS_ReadFile`, then `FS_FreeFile`; at 15 and 16
  in Jedi Outcast's table).

The full interface between the DLLs and the engine, as later read from the
retail executable, is in
[../formats/idtech3/eliteforce-sp-interface.md](../engines/idtech3/formats/eliteforce-sp-interface.md).

## Running the single-player game

`src/engines/idtech3/eliteforce/sp_game_host.{h,cpp}` runs `efgamex86.dll`'s
server game:

- **Loading.** It loads the DLL, calls `GetGameAPI` with native functions
  in the engine's 40 slots, and checks the API version.
- **Starting a level.** It calls `Init` with the map's entity text, lets
  the player join (`ClientConnect`, then `ClientBegin`), and runs frames.
- **Reused from Holomatch.** Collision, entity linking, area portals and
  traces come from the Holomatch host, with the single-player entity layout.
- **Cvars.** The engine's cvar structures live in emulated memory and are
  kept up to date, since the game reads them directly.
- **printf-style calls.** `Printf`, `Error` and `SendServerCommand` are
  formatted from the emulated stack (`src/common/x86/format.cpp`).

`reluva-tool sp-run <game folder> <map>` runs it and reports what the game
did. It finds the DLL beside the game folder unless given `-dll`.

Status: on borg1 the retail game starts the level and runs.

- `Init` parses its data files, starts ICARUS and spawns 561 entities,
  371 of them linked into the world. That's about 83 million
  instructions.
- The player joins.
- Frames run, about 250,000 instructions each.
- The game sets 103 configstrings: the music, models and so on.

The server game also calls into its client half (`cg_viewsize`, sounds),
through the system call function `dllEntry` hands it, so that's set up at
load.

Speed: about 50 million instructions a second in a Release build. A Debug
build is much slower.

## Playing single player

The **Single player** page (`src/engines/idtech3/pages/sp_play_viewer.cpp`)
appears when `efgamex86.dll` is in the install folder. It lists the maps
that aren't Holomatch's and starts at borg1.

- **What it runs.** Each level runs the retail server and client game as
  `sp-run -cgame` does.
- **Frames.** The client game's scenes and pictures are drawn by the same
  scene drawer as the Play page's. The client game's view and scene
  entities are laid out much as in Holomatch: the 112-byte `refdef_t`,
  and a 152-byte `refEntity_t` with Quake III's numbering of its kinds
  (see [eliteforce-sp-interface.md](../engines/idtech3/formats/eliteforce-sp-interface.md),
  "Scene entities").
- **Input.** Keys and mouse go through the player's bindings, as on the
  Play page:
  - movement and buttons become the 28-byte user command;
  - other commands go to the client game first, then the server game.
- **Keys.** Ctrl+R restarts the level, Ctrl+PgUp/PgDn change map, Ctrl+I
  hides the info line, and Esc returns to the menus.

Also done: sound, with the ambient sound sets; wall marks
(`CM_MarkFragments`); lighting from the map's light grid
(`R_LightForPoint`); rotated pictures; saving and loading games, with
the saved-game picture; cinematics; and the menus' single-player screens
(`efuix86.dll`).
